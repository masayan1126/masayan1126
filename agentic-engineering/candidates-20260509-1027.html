C01 国内 DeNA「育てるほど楽になる AI 開発体制を作っている話」

DeNA Engineering（スポーツプラットフォーム部） ／ Koya Nagata（永田） ／ 2026-01-06 ／ 記事を開く

DeNAスポーツプラットフォーム部が、Claude Code/Cursorを「個人補助ツール」に留めずチーム展開するため、CLAUDE.md・AGENTS.md・サブエージェント定義・Skills・docsをリポジトリに集約。レビュー量削減と品質標準化の2軸で設計し、Claude Code ActionsでPR自動レビュー、Serena MCPでコード理解を強化、レビュー指摘を自動でドキュメントに反映する循環を構築。人間レビュー回数 7.2→2.7 回/PR、コメント数 6.0→1.9 件/PR の実数値を提示。
AI を個人の補助ツールにとどめず、チーム全体で活かすには、プロジェクト固有のコンテキストをどう整備・共有するかがポイントになります。
「レビュー → ドキュメント更新 → AI の出力品質向上」というサイクルが回るようになりました。

C02 国内 メルカリ「mercari-pm-agent の設計」

メルカリエンジニアリング ／ 菊池翔吾（Shogo Kikuchi） ／ 2026-04-28 ／ 記事を開く

メルカリのインターンが、PMが行う「問題発見→データ収集→PRD作成→UIモック」をClaude Code Skillsで1セッション内に統合するエージェントを実装。Notion/Slack/Looker/FigmaをMCPで並列接続。Lost in the Middle対策として「振る舞い定義」と「参照データ」を分離。評価基準を実装より先に設計し、未確認データは"Not provided"とラベル付けてハルシネーション抑制、各ステップは人間の明示確認なしに自動進行させない設計を採用。
Markdownを書くだけでは精度は出ません。振る舞いの制約設計と評価サイクルが重要です。
未確認のデータは "Not provided" または "To be validated" とラベルすること

C03 国内 ZOZO「Claude Code Plugins × Atlassian MCP」

ZOZO TECH BLOG（ZOZOMO部 FBZブロック） ／ 杉田 ／ 2026-02-02 ／ 記事を開く

ZOZO ZOZOMO部の杉田氏（社内AI推進兼務）が、Confluence上の開発ガイドラインに対する準拠チェックをClaude Code Plugins化し、Atlassian MCP経由で常に最新ガイドラインを参照する仕組みを構築。プラグインにはSkills/Agents/Hooksを含め、マーケットプレイス機能で全社配布、.claude/settings.jsonのextraKnownMarketplacesで配信。READ_ONLY_MODEで安全運用し、二重管理を回避。手作業確認コスト削減と日常的レビュー実施を両立する組織展開事例。
Claude Codeの機能をチームや組織内部で再利用しやすい形にまとめる拡張機構です
MCPを経由してConfluenceを直接参照することで、実行時点で常に最新の開発ガイドラインを参照できます

C05 国内 freee「数字で振り返る AI 駆動開発 - 後編」

freee Developers Hub ／ JaeSoon（ジェスン） ／ 2025-12-25 ／ 記事を開く

freeeのJaeSoon氏が2025年4月〜12月のAI駆動開発を定量的に振り返る。トークン消費は約7-8倍、1日あたりリクエスト最高16万件超、月間アクティブ600-700エンジニアで安定化。エージェント分布はClaude Code約80%が支配的でCline/Roo Codeを抜く。用途分布はコーディング42%・デバッグ21%・テスト13%・レビュー11%・アーキテクチャ4%。「AI開発マニア制度」で週次PR数・トークン使用量を達成したエンジニアを認定する評価運用を導入。
Claude Codeが圧倒的シェアを占めるようになりました
一週間で一定のPR数とトークン使用量を達成したエンジニアを認定し、Claude Max利用権限を付与する制度です。

C06 海外 Anthropic「Harness design for long-running application development」

Anthropic Engineering ／ Prithvi Rajasekaran ／ 2026-03-24 ／ 記事を開く

Anthropic Labs の Prithvi が、Claude を長時間自律稼働させるためのハーネス設計を解説。単独実行では「コンテキスト窓圧迫」「自己評価の甘さ」で破綻するため、planner / generator / evaluator の 3 役を分割。フロントエンドのような主観品質も評価軸を切り出して採点可能にし、ソロ実行（20分・$9）に対しフルハーネス（6時間・$200）で別次元の成果物を生む。「ハーネスは『モデルが単独でできない』前提を符号化する。その前提を絶えず stress test せよ」と結論。
Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing.

C07 海外 Cloudflare「Orchestrating AI Code Review at scale」

Cloudflare Blog ／ Ryan Skidmore ／ 2026-04-20 ／ 記事を開く

Cloudflare の社内 AI コードレビュー基盤の実装記。7 体の専門 sub-reviewer（security / performance / quality / docs / release / compliance）を OpenCode 経由で並列起動し、coordinator が judge pass で統合。30 日で 131,246 レビュー、48,095 MR、5,169 リポジトリを処理。中央値 3 分 39 秒、平均 $1.19/レビュー、キャッシュヒット率 85.7%。「コードレビューはバグ捕捉とナレッジ共有の好機構だが、エンジニアリングチームを最も確実に詰まらせるボトルネックでもある」と問題提起。
Code review is a fantastic mechanism for catching bugs and sharing knowledge, but it is also one of the most reliable ways to bottleneck an engineering team.
Rather than relying on one model with a massive, generic prompt, we launch up to seven specialised reviewers covering security, performance, code quality, documentation, release management, and compliance with our internal Engineering Codex.

C08 海外 Sentry「Building a Code Review System That Uses Prod Data to Predict Bugs」

Sentry Blog ／ Giovanni Guidini, Kush Dubey, Suejung Shin, Jerry Feng ／ 2025-12-18 ／ 記事を開く

Sentry の AI Code Review の内部アーキテクチャ。Filter → Predict → Package の 3 段パイプラインで、各仮説に対し dedicated agent が Sentry の本番イシュー履歴を「click-into」フローで参照し検証。低信頼/低重大度の予測は除外、過去ダウンボートと埋め込み類似で重複排除。既知の bug PR / safe PR で precision・recall・accuracy を定期評価する eval ループを内蔵。LLM 単発予測ではなく、production telemetry を context として閉じる「データ駆動コードレビュー」の事例。
Because context is king, all agents have access to different tools that provide them with rich context to understand the code being analyzed.
By focusing the verifying agents into a single hypothesis they can deep dive and more correctly assert if that is a valid bug or not.

C09 海外 Vercel「How we made v0 an effective coding agent」

Vercel Blog ／ Max Leiter ／ 2026-01-07 ／ 記事を開く

Vercel が v0 を「効くコーディングエージェント」に仕立てる工夫を公開。最適化指標は「成功生成率」（LLM 生のままだと最大 10% で誤生成）。dynamic system prompt で AI SDK の最新知識を注入、LLM Suspense でストリーム中の find-and-replace（lucide-react アイコン未存在 → 埋め込み類似で最近傍に書き換え 等）、autofixers で AST 解析必要な多ファイル横断問題を後段で 250ms 以内に修正。「system prompt は moat にはならないが、強い steering 機構として残る」と総括。
The primary metric we optimize for is the percentage of successful generations.
Your product's moat cannot be your system prompt.

C10 海外 Shopify「Autoresearch isn't just for training models」

Shopify Engineering ／ David Cortés ／ 2026-04-15 ／ 記事を開く

Shopify エンジニア David Cortés が、Karpathy 由来の「Autoresearch」（GPT-2 を数時間で訓練するための AI 連続改善ループ）を ML 以外の問題（CI ビルド時間短縮）に転用した実話。Slack で社内告知後、CEO Tobi Lütke 自ら 32 commit を当て multi-metric 対応で共著、1 日でコンセプト → 完成。シークレット除去後 OSS 化し X で Tobi が「parse+render を 53% 高速化」と発信、3,600 GitHub Star 超えへ急伸。「ループを回し、数値が下がるのを眺める」というエンジニア像を体現した記事。
53% faster combined parse+render time
It is 7PM and I'm still at my desk... and watch the numbers go down.
